# LifeGame — Security Test Plan

**Status:** CURRENT

## 1. Назначение

test-plan.md определяет порядок, границы и правила полного Security-тестирования LifeGame.

Команда «Запусти полный тест безопасности проекта» означает выполнение актуального test-plan.md совместно с test-manifest.md против фактического состояния проекта.

Security Test Suite предназначен для выявления и классификации уязвимостей, нарушений границ доступа, ошибок конфигурации и расхождений между фактической реализацией и Security-контрактами.

Наличие теста в manifest не является доказательством существования или реализации соответствующей функции.

## 2. Источники истины

При определении того, что именно должно тестироваться, используется приоритет:

1. docs/agent.md;
2. фактический код проекта;
3. тесты проекта;
4. утверждённые Security Architecture и Threat Model;
5. актуальная продуктовая документация;
6. Change Log;
7. устаревшая документация.

Security Test Suite не может самостоятельно считать планируемую архитектуру реализованной.

Если документация и фактическая реализация расходятся, сначала фиксируется фактическое состояние. При невозможности однозначно определить состояние используется REQUIRES VERIFICATION.

## 3. Критическая граница применимости тестов

### 3.1. Тестируется только существующая система

Security-тест запускается только в отношении компонентов, функций, маршрутов, API, таблиц, политик, конфигураций и других механизмов, которые фактически существуют и реализованы в текущем состоянии проекта.

Нельзя запускать тест только потому, что:

- он описан в manifest;
- функция указана в PLANNED/FUTURE документации;
- функция предусмотрена Security Architecture;
- функция ожидается в следующей версии;
- для неё уже подготовлено название теста.

### 3.2. Предварительная проверка применимости

Перед выполнением каждого теста агент обязан определить:

1. существует ли проверяемый компонент;
2. реализована ли проверяемая функция;
3. относится ли она к текущей архитектуре;
4. доступны ли необходимые условия для проверки;
5. не является ли функция только PLANNED, FUTURE, EXPERIMENTAL или DEPRECATED.

Только после этого тест получает статус применимости и может быть выполнен.

### 3.3. Статусы применимости

**APPLICABLE** — проверяемая функция или компонент существует и входит в текущую систему. Тест выполняется.

**NOT APPLICABLE** — проверяемая функция отсутствует в текущей архитектуре или явно не относится к текущему состоянию проекта. Тест не выполняется.

**NOT TESTED** — функция существует, но необходимые условия или окружение для проверки отсутствуют.

**REQUIRES VERIFICATION** — документация, код, конфигурация или тесты дают противоречивые сведения о наличии или состоянии функции.

### 3.4. Planned не означает implemented

Статусы PLANNED, FUTURE, EXPERIMENTAL и аналогичные не превращаются в исполняемый текущий функционал только из-за наличия Security-теста.

Если контроль запланирован, но ещё не реализован:

- тест не запускается как проверка текущего функционала;
- отсутствие будущей функции не считается FAIL;
- при необходимости фиксируется как покрытие будущего требования или REQUIRES VERIFICATION;
- фактический статус должен быть отражён в итоговом отчёте.

### 3.5. Запрет на искусственное создание объекта тестирования

Security Test Suite не должен создавать отсутствующую продуктовую функцию, чтобы затем проверить её как часть текущей системы.

Например, если custom device/session management ещё не реализован, нельзя создавать временную реализацию такого механизма внутри теста и выдавать её результат за проверку LifeGame.

Тест может создавать только необходимые тестовые данные и тестовые условия для реально существующего механизма.

### 3.6. Расхождение документации и реализации

Если документ обозначает функцию как CURRENT/IMPLEMENTED, но код её не подтверждает:

REQUIRES VERIFICATION.

Если код содержит функцию, отсутствующую в актуальной документации:

1. фиксируется расхождение;
2. определяется фактическое состояние по коду и тестам;
3. существующая функция может быть протестирована;
4. документация не изменяется автоматически в рамках Security-теста.

## 4. Область полного теста

Полный Security-тест включает применимые проверки:

1. Static Security;
2. Authentication;
3. Authorization;
4. Web Security;
5. Infrastructure;
6. Threat Model Regression;
7. итоговый анализ и отчёт.

Конкретные проверки определяются test-manifest.md.

## 5. Подготовка

Перед началом теста необходимо определить:

- текущую ветку;
- текущий commit/revision;
- фактическую структуру проекта;
- доступное тестовое окружение;
- тестовые аккаунты;
- доступные конфигурации и интеграции;
- область проверки;
- ограничения окружения;
- применимость каждого manifest-теста.

Для полного теста должна быть зафиксирована исходная точка, чтобы результаты можно было воспроизвести.

Если необходимое окружение отсутствует, соответствующая проверка не считается пройденной.

## 6. Правила безопасности выполнения

### SAFE

Разрешены:

- чтение исходного кода;
- анализ документации;
- анализ конфигурации;
- dependency audit;
- анализ миграций;
- поиск секретов и опасных паттернов;
- анализ GitHub Actions;
- read-only проверки.

SAFE-проверки не должны изменять состояние проекта или пользовательские данные.

### CONTROLLED

Разрешены только в ограниченном тестовом окружении:

- регистрация тестовых пользователей;
- login/logout;
- verification/resend;
- session tests;
- authorization/RLS tests;
- controlled malicious input;
- проверка rate limiting;
- проверка HTTP security behaviour;
- controlled cross-user access attempts.

Используются только тестовые данные и минимально необходимый объём запросов.

### DESTRUCTIVE

К этой категории относятся:

- удаление данных;
- destructive database operations;
- destructive migrations;
- массовые операции с аккаунтами;
- нагрузочные атаки;
- действия, способные повредить production-данные или инфраструктуру.

DESTRUCTIVE-проверки не выполняются автоматически в рамках команды полного теста.

## 7. Стандарт выполнения каждого теста

Каждая применимая проверка выполняется по последовательности:

1. PRECONDITION — подтверждение существования объекта проверки и условий запуска.
2. EXECUTION — выполнение предусмотренных действий.
3. OBSERVATION — фиксация фактического поведения.
4. EXPECTED RESULT — ожидаемое безопасное поведение.
5. ACTUAL RESULT — фактический результат.
6. STATUS — итоговый статус проверки.
7. EVIDENCE — подтверждающие данные.
8. SEVERITY — уровень проблемы, если выявлено отклонение.

Нельзя присваивать PASS, если необходимое наблюдение не было фактически выполнено.

## 8. Результаты тестов

Используются следующие статусы:

- PASS — проверка выполнена, ожидаемое безопасное поведение подтверждено;
- FAIL — обнаружено подтверждённое нарушение;
- WARNING — обнаружено потенциально опасное состояние, не подтверждённое как уязвимость;
- NOT TESTED — проверка применима, но не была выполнена;
- NOT APPLICABLE — проверка не относится к текущей реализации;
- REQUIRES VERIFICATION — состояние невозможно подтвердить однозначно.

PLANNED или отсутствие будущей функции сами по себе не являются FAIL.

## 9. Severity

Для подтверждённых проблем используются:

- CRITICAL — критическое нарушение безопасности с потенциально тяжёлыми последствиями;
- HIGH — существенная уязвимость с высоким риском;
- MEDIUM — значимое нарушение с ограниченным или условным воздействием;
- LOW — малозначимый дефект безопасности;
- INFO — наблюдение без подтверждённой уязвимости.

Severity присваивается проблеме, а не самому факту наличия теста.

## 10. Этапы полного теста

### Phase 0 — Preparation

Проверяются:

- revision;
- структура проекта;
- актуальность Security-документации;
- тестовое окружение;
- применимость manifest;
- ограничения выполнения.

### Phase 1 — Static Security

Проверяются применимые:

- secrets/credentials;
- зависимости;
- environment/configuration exposure;
- security-sensitive patterns;
- Clean Architecture security boundaries;
- GitHub Actions security configuration.

### Phase 2 — Authentication

Проверяются только существующие механизмы:

- registration;
- login;
- email verification;
- verification resend;
- logout;
- session handling;
- current-session isolation;
- password recovery;
- authentication abuse/rate limiting.

Если механизм отсутствует или является только планируемым, применяется правило раздела 3.

### Phase 3 — Authorization

Проверяются:

- cross-user read isolation;
- cross-user update isolation;
- cross-user delete isolation;
- client userId manipulation;
- PostgreSQL RLS;
- system/private data boundary.

Проверка выполняется только для реально существующих user-scoped ресурсов и механизмов.

### Phase 4 — Web Security

Проверяются применимые:

- reflected/stored XSS;
- DOM XSS;
- CSRF exposure;
- CORS;
- security headers;
- URL/query manipulation;
- input validation;
- error/data leakage;
- browser storage exposure;
- frontend secret exposure.

### Phase 5 — Infrastructure

Проверяются:

- Supabase security configuration;
- database grants and policies;
- migration security;
- public/private resource exposure;
- deployment security;
- CI/CD security.

Проверяются фактически используемые сервисы и конфигурации, а не будущая инфраструктура.

### Phase 6 — Threat Model Regression

Фактическое состояние сравнивается с:

- SECURITY_ARCHITECTURE.md;
- THREAT_MODEL.md;
- docs/project-state.md;
- актуальной архитектурой проекта.

Проверяется, не выдаются ли требования, планы или целевые механизмы за реализованные.

### Phase 7 — Final Analysis

Для каждого FAIL и существенного WARNING фиксируются:

- уникальный ID;
- severity;
- компонент;
- условие;
- шаги воспроизведения;
- expected result;
- actual result;
- evidence;
- security impact;
- recommendation;
- ограничение проверки, если оно есть.

## 11. Evidence

Доказательствами могут быть:

- конкретные файлы и строки;
- результаты тестов;
- конфигурация;
- SQL policies/grants;
- HTTP responses;
- browser/network observations;
- GitHub Actions results;
- migration state;
- воспроизводимые шаги;
- commit/revision.

Утверждение без проверяемого evidence не считается подтверждённым Security finding.

Секреты, токены, пароли и другие чувствительные значения не должны включаться в отчёт в открытом виде.

## 12. Критерии завершения полного теста

Полный тест считается завершённым только если:

1. обработаны все обязательные применимые проверки manifest;
2. каждому тесту присвоен результат;
3. непройденные проверки явно отмечены;
4. CRITICAL и HIGH проблемы выделены отдельно;
5. найденные расхождения имеют evidence;
6. фактическая реализация сверена с Security Architecture и Threat Model;
7. тесты на отсутствующие функции не выдаются за выполненные;
8. ограничения окружения отражены в отчёте.

Если обязательная проверка не выполнена, аудит нельзя выдавать как полностью успешный.

## 13. Формат итогового отчёта

Итог должен содержать:

### Общая информация

- дата и время;
- commit/revision;
- окружение;
- область проверки;
- ограничения.

### Сводка

- количество PASS;
- количество FAIL;
- количество WARNING;
- количество NOT TESTED;
- количество NOT APPLICABLE;
- количество REQUIRES VERIFICATION;
- количество CRITICAL;
- количество HIGH.

### Применимость

Отдельно указываются проверки, которые не запускались из-за отсутствия соответствующей реализации.

### Findings

Для каждого подтверждённого finding:

- ID;
- severity;
- компонент;
- описание;
- воспроизведение;
- expected;
- actual;
- evidence;
- impact;
- recommendation.

### Ограничения

Фиксируются недоступные окружения, отсутствующие условия, непройденные проверки и другие причины неполного покрытия.

## 14. Работа с manifest

test-manifest.md является картой Security-проверок.

Каждый manifest-тест должен иметь:

- уникальный ID;
- цель;
- уровень воздействия;
- статус;
- условия применимости;
- ожидаемый результат;
- способ получения evidence.

CURRENT у manifest-теста означает только, что проверка входит в текущий набор Security Test Suite.

CURRENT не означает, что проверяемая защита уже реализована.

Если для проверки требуется отсутствующая функция, применяется раздел 3 настоящего документа.

## 15. Граница ответственности

Security Test Suite:

- анализирует фактическое состояние проекта;
- выявляет и классифицирует Security-проблемы;
- фиксирует evidence;
- указывает расхождения и ограничения.

Security Test Suite не изменяет автоматически:

- бизнес-логику;
- архитектуру;
- UI/UX;
- Design System;
- формулы;
- базу данных;
- Security implementation;
- production-конфигурацию.

Исправление выявленных проблем выполняется отдельной согласованной задачей.

Результат Security-теста не является разрешением на изменение архитектуры или реализации без отдельного согласования.
