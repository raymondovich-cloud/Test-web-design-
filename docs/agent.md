# LifeGame — Agent Rules

## 1. Приоритет документа

`docs/agent.md` — главный нормативный документ проекта.

Он определяет правила работы с архитектурой, кодом и документацией. Фактическое состояние проекта определяется по приоритету:

1. `docs/agent.md`;
2. фактический код проекта;
3. тесты;
4. утверждённые архитектурные решения и ADR;
5. актуальная продуктовая документация;
6. Change Log;
7. устаревшие документы.

Если документация расходится с фактическим кодом, расхождение необходимо зафиксировать и устранить в документации после проверки.

## 2. Clean Architecture

Первостепенное архитектурное правило проекта — соблюдать Clean Architecture.

Бизнес-логика и правила предметной области должны быть изолированы от UI, платформ, инфраструктуры и способов хранения данных.

Архитектура LifeGame включает:

- `core/`;
- `domain/`;
- `application/`;
- `presentation/`;
- `infrastructure/`;
- `memory/`;
- отдельный вычислительный слой/подсистему `index/`;
- независимую Design System `design/`.

`index/` является отдельной архитектурной подсистемой расчётных показателей и не должен смешиваться с пользовательским интерфейсом, постоянным хранением или сырыми Domain-данными.

### 2.1. Границы слоёв

**Core**
- содержит наиболее стабильные общие механизмы и контракты;
- не зависит от Presentation, Application, конкретных Domain-модулей, Infrastructure, Memory или Design System.

**Domain**
- содержит бизнес-правила и предметную логику;
- не хранит пользовательское состояние;
- не обращается напрямую к Memory, Infrastructure, UI, хранилищам, внешним SDK или конкретным криптографическим реализациям;
- Domain-модули не должны напрямую зависеть друг от друга.

**Application**
- координирует прикладные сценарии;
- связывает Domain, Memory, Index и Presentation через разрешённые контракты;
- не должен становиться заменой Domain.

**Presentation**
- отвечает за UI и пользовательское взаимодействие;
- не содержит бизнес-правил;
- не обращается напрямую к базе данных, Memory или хранилищу;
- не обходит Application для изменения состояния.

**Infrastructure**
- содержит технические реализации: базы данных, сеть, Browser API, внешние API, техническое логирование, криптографические реализации и другие технические механизмы;
- технические детали не должны проникать в Domain.

**Memory**
- отвечает за пользовательское и системное состояние в пределах определённых контрактов;
- не является источником бизнес-правил;
- не является самостоятельным источником авторизации.

**Index**
- содержит расчётные показатели, производные от данных, полученных через разрешённые прикладные контракты;
- не должен превращаться в хранилище пользовательских данных;
- не должен содержать UI-логику.

**Design System**
- находится в `source/design/`;
- является независимой визуальной системой;
- не содержит бизнес-логики;
- не зависит от Domain, Application, Infrastructure или Memory.

Общее направление зависимостей: внешний слой может использовать внутренние абстракции, но внутренний слой не должен зависеть от внешних технических деталей.

## 3. Один файл = одна ответственность

Каждый файл должен иметь одну чётко определённую ответственность.

Не объединять без необходимости:

- независимые бизнес-задачи;
- разные архитектурные слои;
- UI и бизнес-логику;
- UI и Infrastructure;
- несвязанные функции.

## 4. Имена файлов и папок

Все новые и изменяемые файлы и папки должны иметь имена со строчной буквы.

Исключение: числовые директории дат, например `6.10.2026`.

Существующие исторические имена не переименовываются только ради этого правила.

## 5. Версионирование файлов

Каждый создаваемый или изменяемый файл, кроме Change-файлов, должен иметь версию в начале файла.

Формат:

`file.js — Version 1.0`

При следующем изменении версия увеличивается на `0.1`.

Новому файлу присваивается `1.0`.

Версия обязательна при любом изменении содержимого.

## 6. Change Log и атомарность изменений

Один пользовательский запрос, который приводит к изменению репозитория, является одной атомарной операцией.

Каждая такая операция создаёт **ровно один Git commit и ровно один новый Change-файл**.

Commit и Change-файл относятся к одной и той же операции и имеют общую идентичность:

`<область>/<краткая суть>/<дата>` — для commit;

`<область>/<краткая суть>/<дата>-<время>.md` — для Change-файла.

Пример:

`Design/изменение отступов/10.26`

`Design/изменение отступов/10.26-12.44.md`

Правила:

- `<область>` определяет область проекта или архитектурный контур изменения;
- `<краткая суть>` однозначно описывает изменение;
- дата входит в идентичность операции;
- время фиксируется только в имени Change-файла;
- Change-файл входит в тот же commit, что и остальные изменения операции;
- нельзя создавать отдельный commit только для Change-файла;
- один пользовательский запрос может изменять несколько файлов, но все изменения запроса и его единственный Change-файл должны попасть в один commit;
- новый запрос после завершения предыдущего изменения всегда создаёт новую атомарную операцию, даже если он отменяет, возвращает или изменяет результат предыдущего запроса;
- более ранние Change-файлы не переименовываются только ради перехода на новый формат.

Новые Change-файлы создаются только в закреплённой папке дня рабочей сессии:

`docs/changes/D.M.YYYY/`

Change-файл должен содержать:

- дату и точное время;
- `MSK (UTC+03:00)`;
- пользовательский запрос;
- изменённые файлы;
- версии до и после;
- описание изменения;
- причину;
- принятые архитектурные решения;
- итоговый статус.

Change-файлы не участвуют в обычном версионировании и не создают рекурсивный Change.

## 7. Согласование изменений

Для изменения репозитория применяется двухэтапный процесс:

1. анализ и согласование;
2. реализация после явного подтверждения пользователя.

До согласования изменения в репозиторий не вносятся.

После согласования необходимо:

1. повторно проверить актуальное состояние;
2. изменить только необходимые файлы;
3. обновить версии;
4. создать один Change-файл;
5. проверить имена;
6. зафиксировать результат в Git одним commit.

Если пользователь прямо просит выполнить конкретное изменение без обсуждения, реализация может быть выполнена сразу, но остальные правила сохраняются.

### 7.1. Рабочая ветка и тестовая среда

Для всех ближайших изменений LifeGame действует следующий рабочий процесс:

- Все новые изменения вносятся в существующую ветку `feature/pwa-static-cache`. Не создавать дополнительные рабочие ветки без отдельного указания пользователя.
- Проверка изменений выполняется через CI и отдельную тестовую публикацию в репозитории `raymondovich-cloud/Test-web`.
- Основная ветка `main` сохраняется без изменений и используется как защищённая базовая версия.
- Не объединять `feature/pwa-static-cache` с `main`, не выполнять merge PR и не переносить изменения в `main` без отдельного явного согласования пользователя.
- Успешная тестовая публикация или прохождение CI сами по себе не являются разрешением на merge.
- Перед каждой задачей проверять фактическое состояние рабочей ветки и тестовой среды; соблюдать атомарность изменений, архитектурные правила и Change Log из раздела 6.

## 8. Статусы проектной информации

Используются следующие статусы:

- **CURRENT** — подтверждено текущим кодом, тестами или другими актуальными источниками и действует сейчас.
- **BASELINE** — явно зафиксированная пользователем стабильная основа проекта. BASELINE не означает автоматического совпадения с CURRENT.
- **IMPLEMENTED** — конкретная функциональность или решение подтверждено как реализованное.
- **PLANNED** — согласованное изменение, которое ещё не реализовано.
- **EXPERIMENTAL** — эксперимент, не закреплённый как основа.
- **FUTURE** — возможное или отложенное направление, не являющееся текущим планом реализации.
- **DEPRECATED** — устаревшая информация, сохранённая для истории.
- **REMOVED** — ранее существовавшая функциональность или решение, которое удалено.
- **REQUIRES VERIFICATION** — недостаточно подтверждений для утверждения факта.

Если факт нельзя подтвердить, его нельзя додумывать. Используется `REQUIRES VERIFICATION`.

### 8.1. Роли документов

- `docs/agent.md` — только нормативные правила проекта.
- `docs/fixed-version-project.md` — полный BASELINE из явно зафиксированных решений.
- `docs/project-state.md` — CURRENT-состояние, подтверждаемое кодом и тестами.
- `docs/changes/` — история изменений по пользовательским запросам.
- `docs/sessions/` — контекст отдельных рабочих сессий.

Ни один из этих документов не подменяет фактическую проверку кода и тестов там, где она необходима.

История не становится CURRENT автоматически. BASELINE не становится CURRENT автоматически. PLANNED и FUTURE не считаются реализованными без подтверждения.

## 9. Finance — терминология

Официальная терминология финансового индекса проекта:

**FSI 3.1 — Financial Stability Index.**

Обозначение `IFS 3.0` больше не используется как официальное название.

Устаревшее обозначение `IFS-1000` не используется для текущего состояния и может сохраняться только в историческом контексте.

Finance DATA включает:

1. Assets / Активы;
2. Actual income / Фактически заработанно;
3. Financial burden / Финансовая нагрузка;
4. Mandatory expenses / Обязательные траты;
5. Financial cushion / Финансовая подушка;
6. FSI 3.1 / Financial Stability Index.

Finance Main и Finance DATA документируются раздельно.

Assets не должны автоматически трактоваться как ликвидные средства. Ликвидность определяется отдельно.

Financial burden различает:

- `debt` — задолженность;
- `payment` — регулярный платёж.

## 10. Design System

Design System находится в `source/design/` и реализуется отдельными CSS-модулями.

Она включает:

- tokens;
- foundation;
- components;
- patterns;
- themes.

Design System:

- не содержит бизнес-логики;
- не зависит от Domain, Application, Infrastructure или Memory;
- является единым источником повторно используемых визуальных правил.

Не создавать монолитный `design.js` или JS-файлы для хранения визуальных правил.

## 11. Пользовательские и системные данные

Пользовательские и системные данные должны быть разделены логически и архитектурно.

Пользовательские данные:

- Finance;
- Health;
- Development;
- Profile.

Системные данные:

- логи;
- аудит;
- диагностика;
- миграции;
- системные события.

Правила доступа, хранения, шифрования, аудита и удаления для этих категорий не должны смешиваться.

## 12. Security

Security является архитектурной частью LifeGame.

`SECURITY_ARCHITECTURE.md` и `THREAT_MODEL.md` являются отдельными security-контрактами и не должны молча изменяться в рамках общего документационного аудита.

Security-документы должны разделять фактическую реализацию и будущие требования.

## 13. Security Test Suite

`docs/security/test.security/` — нормативный контур Security-тестирования.

Он определяет:
- порядок полного Security-теста;
- manifest обязательных проверок;
- уровни воздействия SAFE, CONTROLLED и DESTRUCTIVE;
- правила фиксации результатов и evidence.

Команда «Запусти полный тест безопасности проекта» означает выполнение актуального `test-plan.md` и `test-manifest.md` с проверкой фактического кода, тестов и Security-контрактов.

Наличие теста не означает наличие защищающей функции. Реализация подтверждается только фактическим результатом проверки.

Security Test Suite не изменяет автоматически код, архитектуру, базу данных, Security implementation или production-конфигурацию. Исправления выполняются отдельной согласованной задачей.

### 13.1. Документационный аудит

Перед изменением документации необходимо:

1. прочитать `docs/agent.md`;
2. изучить структуру проекта;
3. проверить существующую документацию;
4. сверить спорные факты с кодом и тестами;
5. найти противоречия, дубли и устаревшие сведения;
6. определить фактическое состояние;
7. внести минимально необходимое изменение;
8. обновить версию изменённых документов;
9. создать один Change-файл;
10. зафиксировать результат.

Не добавлять сведения ради объёма.

Если факт невозможно подтвердить — использовать `REQUIRES VERIFICATION`.

## 14. Принцип качества

Документация должна быть:

- точной;
- актуальной;
- краткой;
- однозначной;
- структурированной;
- проверяемой;
- пригодной для человека и AI-агента;
- согласованной с фактическим кодом.

Документация не должна выдавать планы, эксперименты или исторические записи за реализованный функционал.
