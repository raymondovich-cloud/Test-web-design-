# LifeGame — повторный аудит безопасности дневника тренировок

**Дата:** 10.10.2026  
**Время:** 15:26 МСК  
**Ветка:** `feature/pwa-static-cache`  
**Проверенная база кода:** `d40c7721595fcf2971e068b4cbe41ac5b6a0e49a`  
**Статус:** REVIEW REQUIRED — критических подтверждённых межпользовательских обходов в просмотренных путях не обнаружено, но интеграцию хранения нельзя считать готовой к production.

## 1. Объём

Проверены HTTP handler и его тесты, Supabase repository и unit-тесты, миграция PostgreSQL, database tests, AES-256-GCM/KMS adapter, security contract и Database Tests workflow. Проверка только чтения; код приложения, удалённая Supabase-база, миграции, секреты и облачные ресурсы не изменялись.

## 2. Выводы

### Finding T-01 — authenticated клиент может обходить Application-сценарии записи

**Приоритет: высокий для целостности данных; требует решения до production.**

Миграция выдаёт роли `authenticated` прямые `SELECT, INSERT, UPDATE` grants на `public.training_sessions`. RLS корректно ограничивает строки владельцем, а trigger проверяет владельца, неизменность identity, переходы статуса и revision. Однако сама база не различает запросы, пришедшие через Training Sessions Edge Function, и прямые запросы к Supabase REST с пользовательским JWT.

Поэтому пользователь может миновать Domain/Application-валидацию и отправить собственные произвольные поля шифрованного конверта или несовместимые метаданные. Это не подтверждает чтение чужих данных, но создаёт риск повреждения собственных записей и последующей невозможности расшифрования.

**Рекомендация:** до включения production-пути определить единственную доверенную границу записи. Предпочтительный вариант — закрыть прямые пользовательские INSERT/UPDATE и выполнять записи через контролируемый серверный путь с повторной проверкой пользователя и атомарной CAS-операцией. Но Edge Function сейчас использует пользовательский клиент, а service-role обход RLS ещё не спроектирован. Не менять grants/ключи наугад: сначала спроектировать безопасную схему, тесты и минимально привилегированную серверную авторизацию. Любая настройка секретов/деплой требует отдельной проверки бесплатности и согласования.

### Finding T-02 — server-side KMS wiring не готово к развёртыванию

**Приоритет: блокер production.**

`index.ts` требует AWS access key и secret key как env-переменные. Ни AWS KMS, ни секреты, ни Edge Function не подключены. Долгоживущие AWS credentials в Supabase secrets расширили бы область риска. Unit-тесты используют mock KMS и не подтверждают реальные IAM policies, AWS Encryption Context, права ключа, ротацию или восстановление данных.

**Рекомендация:** не развёртывать текущий endpoint и не добавлять credentials. Сначала оценить бесплатные/уже доступные варианты хранения ключей. Если подходящего бесплатного варианта, удовлетворяющего модели угроз, нет — остановиться и согласовать стоимость и архитектуру. Не заменять KMS статическим ключом в коде или базе.

### Finding T-03 — открытые поля раскрывают поведенческие метаданные

**Приоритет: умеренный; осознанный остаточный риск.**

`session_date`, `status`, timestamps и факт существования записи не шифруются. Security contract уже признаёт, что эти поля раскрывают частоту тренировок. RLS ограничивает доступ владельцем, но администраторы/роли с повышенными полномочиями инфраструктуры остаются в доверенной зоне.

**Рекомендация:** подтвердить это как осознанный privacy trade-off. Если нужна защита частоты тренировок даже от операторов БД, потребуется отдельная архитектура: шифрование большего объёма метаданных и другой подход к календарным выборкам.

### Finding T-04 — нет live crypto/persistence integration test

**Приоритет: блокер production, не блокер локальной разработки.**

Текущий CI подтверждает локальные SQL/RLS тесты и unit-тесты с mock encryption/KMS. Он не подтверждает совместимость Edge Runtime, Supabase Auth и настоящего KMS, а также end-to-end round trip ciphertext через реальное хранилище. Удалённая миграция не применялась, Edge Function не развёрнута — это правильно для текущего бесплатного этапа.

**Рекомендация:** оставить integration gate закрытым до утверждения провайдера, модели секретов и бюджета. Затем запускать smoke test только в изолированном бесплатном/одобренном окружении с тестовыми данными.

## 3. Что выглядит корректно в проверенных путях

- HTTP handler требует Bearer token и повторно проверяет его через Supabase Auth.
- В запросах к репозиторию user scope берётся из проверенной identity; чужой user ID отвергается до запроса.
- RLS ограничивает строки текущим владельцем; database tests проверяют изоляцию User A/User B и запрет anon.
- SQL trigger фиксирует владельца и ID, валидирует переходы статуса и сам увеличивает revision.
- Repository выполняет compare-and-swap через фильтр ожидаемой revision.
- AES-GCM использует AAD, nonce 12 байт и tag 16 байт; ошибки расшифрования не должны возвращать частичный payload.
- Handler ограничивает размер тела, не кэширует ответы и не выдаёт внутренние сообщения исключений.
- В логах handler передаётся только код события, а не payload или токены.

Это результаты статического чтения и имеющихся тестов, а не доказательство полного отсутствия уязвимостей.

## 4. Следующие действия

1. Спроектировать закрытие прямой записи в таблицу без ослабления RLS и без неоговорённых секретов.
2. Добавить тест, который доказывает невозможность записи в обход доверенного Application/HTTP пути.
3. Проверить строгую валидацию encrypted envelope и соответствие AAD полям строки.
4. Зафиксировать метаданные как отдельный privacy trade-off.
5. Повторно проверить CI после изменений; до того не заявлять интеграцию production-ready.
