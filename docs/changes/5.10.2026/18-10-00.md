# Проверка Finance Supabase Persistence

**Дата:** 05.10.2026  
**Время (Москва):** 18:10:00

## Проверено

### 1. PostgreSQL storage

Проверены шесть Finance таблиц:

- finance_assets
- finance_actual_earnings
- finance_burdens
- finance_mandatory_expenses
- finance_cushions
- finance_asset_snapshots

На момент проверки все таблицы пусты. Это ожидаемо: проверка не создавала тестовые пользовательские финансовые данные.

### 2. RLS

Проверены PostgreSQL policies через pg_policies.

Для пяти current-state таблиц присутствуют SELECT/INSERT/UPDATE/DELETE policies собственного пользователя.

Для snapshots присутствуют SELECT/INSERT policies собственного пользователя.

Условие:

`auth.uid() = user_id`

### 3. Hydration

Supabase Finance Memory Adapter загружает все пять Finance коллекций и Assets snapshots перед authenticated render.

### 4. Persistence

Проверено по коду:

- create → INSERT → cache update;
- update → UPDATE → cache update;
- delete → DELETE → cache update;
- snapshots → INSERT → cache update;
- reload → hydrate из PostgreSQL.

### 5. Domain isolation

Domain не импортирует Supabase, Memory или userId.

### 6. User isolation

Adapter всегда формирует запросы с userId, а PostgreSQL RLS дополнительно ограничивает доступ через auth.uid().

### 7. Liquid / Illiquid

Application продолжает вычислять liquidAssets и illiquidAssets из текущего Memory state.

FSI остаётся derived value и не хранится как primary state.

### 8. Исправленный дефект

Обнаружен и исправлен недостаток:

Assets delete ранее не ожидал сохранения snapshot.

Теперь используется `await memory.saveAssetsSnapshot(...)`.

## Не пройдено физически

В текущей среде невозможно выполнить полноценный browser E2E с реальной пользовательской сессией.

Поэтому физически не подтверждены:

- создание записи через UI;
- reload браузера с восстановлением конкретной записи;
- logout/login конкретного пользователя;
- cross-user RLS через две реальные auth-сессии;
- фактический UI lifecycle Liquid → Illiquid → Liquid.

GitHub Actions workflow для commit также отсутствует, поэтому автоматический CI run не предоставлен.

## Обнаруженное архитектурное ограничение

Текущая последовательность Assets mutation:

1. INSERT/UPDATE/DELETE current state;
2. отдельный INSERT snapshot.

Это два независимых SQL запроса.

Следовательно, при сетевом сбое между ними возможна ситуация:

- current state изменился;
- snapshot не записался.

Это не нарушает RLS, но нарушает требование полной транзакционной целостности current state + history.
