# Изменение авторизации LifeGame

Дата и время создания: 04.10.2026 01:26:24 MSK (UTC+03:00)

## Пользовательский запрос

Продолжить настройку и запустить регистрацию/авторизацию пользователей в тестовом режиме, сохранив требования `docs/agent.md`, Clean Architecture, DDD и премиальный стандарт проекта.

## Что изменено

1. Добавлен отдельный provider-independent код ошибки для неподтверждённого email.
2. Ошибка Supabase `email_not_confirmed` теперь корректно преобразуется Infrastructure-слоем и передаётся в Presentation без зависимости UI от Supabase.
3. Ошибка ограничения запросов HTTP 429 получила единое понятное поведение.
4. Добавлена возможность повторной отправки письма подтверждения из экранов регистрации и авторизации.
5. Регистрация корректно различает активную сессию и состояние ожидания подтверждения email.
6. Logout, получение текущей сессии, сброс пароля, смена пароля и повторная отправка подтверждения теперь нормализуют ошибки Infrastructure-слоем вместо передачи Supabase-ответов выше архитектурной границы.
7. Сессионный ответ Supabase нормализуется до минимального provider-independent объекта.
8. Токены сессии не передаются в Application/Presentation.
9. Реальная Supabase Auth остаётся единственным механизмом идентификации. Fake-auth, localStorage-аутентификация и обход Supabase не добавлялись.

## Архитектурные решения

- Domain не получил зависимостей от Supabase или browser API.
- Application не получил зависимостей от Supabase.
- Supabase остаётся только в Infrastructure.
- Redirect URL продолжает задаваться Web Composition Root.
- Секретные ключи и service role key в клиентский код не добавлялись.
- Поведение рассчитано на оба тестовых режима Supabase: с обязательным подтверждением email и с отключённым Confirm email.

## Проверка

Локальный запуск Node.js тестов из среды выполнения был предпринят, но сетевой доступ среды к GitHub недоступен, поэтому локальный `git clone` выполнить не удалось.

Изменения зафиксированы непосредственно в GitHub. После публикации необходимо проверить GitHub Actions и фактический сценарий регистрации в браузере.

## Следующий обязательный шаг тестирования

Для тестового режима, в котором пользователь должен сразу попасть в приложение после регистрации, в Supabase временно отключается `Confirm email` в настройках Email Provider.

Для режима с подтверждением email текущая реализация поддерживает ожидание письма и повторную отправку, но встроенный Supabase SMTP имеет ограничения частоты отправки. Для production необходимо перейти на Custom SMTP.

## Итоговый статус

Кодовая часть тестовой регистрации/авторизации обновлена. Реальный Supabase Auth сохранён. Требуется финальная проверка в браузере после публикации и, при необходимости, временное отключение `Confirm email` в Supabase для тестирования регистрации без почты.
