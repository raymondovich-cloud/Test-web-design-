# Health Index 1.0 — методология

**Статус:** DEPRECATED как целевая методология. Код Health Index 1.0 остаётся legacy-реализацией до отдельной миграции; экспериментальная модель Activity & Training описана в `docs/health-activity-training-1.0.md` и пока не подключена к пользовательскому индексу.  
**Версия модели:** 1.0  
**Версия документа:** 1.2  
**Дата:** 08.10.2026

## 1. Назначение

Health Index — производный показатель LifeGame для оценки устойчивости повседневной системы здоровья, активности и восстановления. Он не является медицинским диагнозом, клиническим инструментом или заменой врача.

Цель индекса — ответить на прикладной вопрос: **насколько устойчиво пользователь поддерживает сон, физическую активность, тренировочный режим, питание и образ жизни в наблюдаемом периоде?**

Модель строится так:

RAW DATA → METRICS → NORMALIZATION → FACTORS → COVERAGE / CONFIDENCE → HEALTH INDEX → CONSTRAINTS → DIAGNOSIS → RECOMMENDATION

## 2. Шкала

Итоговый индекс: **0–100**.

- **0 ≤ H < 40** — Critical
- **40 ≤ H < 60** — Weak
- **60 ≤ H < 75** — Attention
- **75 ≤ H < 90** — Good
- **90 ≤ H ≤ 100** — Excellent

Границы являются продуктовой шкалой, а не медицинскими порогами.

## 3. Факторы и веса

| Фактор | Вес |
|---|---:|
| Recovery / Восстановление | 25% |
| Activity / Повседневная активность | 20% |
| Training / Тренировочная система | 15% |
| Nutrition / Питание | 15% |
| Lifestyle / Образ жизни | 15% |
| Body / Параметры тела | 10% |

Сумма весов = 100%.

Recovery получает максимальный вес, поскольку устойчивость восстановления является ключевым компонентом повседневной системы. Body получает минимальный прямой вес: масса, рост и другие физиологические показатели не должны автоматически доминировать над поведением пользователя.

## 4. Расчёт фактора

Каждый фактор состоит из нормализованных метрик со значениями от 0 до 100.

Для фактора f:

F_f = Σ(w_i × m_i) / Σ(w_i)

где m_i — нормализованный балл метрики, а w_i — её вес внутри фактора.

### 4.1 Target-band normalization

Для большинства метрик используется целевой диапазон, а не принцип «чем больше, тем лучше».

Общая модель:

- внутри целевого диапазона → 100;
- ниже диапазона → плавное снижение к 0 по нижней границе;
- выше диапазона → либо мягкое снижение, либо плато 100, если превышение само по себе не является отрицательным сигналом;
- за пределами допустимой области → 0.

Функция конкретной метрики должна задаваться её собственным профилем. Универсальная функция не применяется автоматически ко всем данным.

Target bands являются **продуктовыми параметрами**, основанными на доступных рекомендациях и выбранной логике LifeGame. Они не являются медицинскими диагнозами или индивидуальными лечебными нормами.

## 5. Профили нормализации метрик

### 5.1 Recovery — 25%

#### Sleep duration

Для взрослых в LifeGame используется базовая целевая зона **7–9 часов**. CDC рекомендует взрослым 18–60 лет получать не менее 7 часов сна; целевой диапазон LifeGame шире и используется как продуктовая зона оптимального восстановления.

Профиль:

| Средняя продолжительность | Score |
|---|---:|
| <4 ч | 0–10 |
| 4–5 ч | 10–35 |
| 5–6 ч | 35–65 |
| 6–7 ч | 65–90 |
| 7–9 ч | 100 |
| 9–10 ч | 90–100 |
| 10–11 ч | 70–90 |
| 11–12 ч | 40–70 |
| >12 ч | требует дополнительной интерпретации |

Для сна выше целевого диапазона применяется более мягкое снижение, чем для выраженного недосыпа. Это принципиально: LifeGame не должен трактовать «больше сна» как автоматически плохой показатель.

#### Sleep regularity

Оценивается отдельно от длительности.

Основные входы:
- время отхода ко сну;
- время пробуждения;
- вариативность этих значений за 28 дней.

Базовый профиль:

| Средняя вариативность режима | Score |
|---|---:|
| ≤30 мин | 100 |
| 30–60 мин | 75–100 |
| 60–90 мин | 50–75 |
| 90–120 мин | 25–50 |
| >120 мин | 0–25 |

Это продуктовая шкала регулярности, а не клинический порог.

#### Subjective recovery

Пользовательская оценка восстановления по шкале 0–10 преобразуется линейно в 0–100.

#### Resting HR

Используется только при наличии достаточной последовательности наблюдений.

LifeGame не задаёт универсального «идеального» пульса. Основной сигнал — **отклонение от личного базового уровня пользователя**.

Для первой реализации:
- baseline = устойчивое медианное значение за доступный период;
- небольшое отклонение от baseline → высокий score;
- устойчивое значительное отклонение → снижение Recovery;
- единичное отклонение не должно резко менять индекс.

#### HRV

HRV является optional metric.

Он используется только при:
- корректном источнике;
- сопоставимом способе измерения;
- достаточной серии наблюдений.

Абсолютное значение HRV без персонального baseline не должно автоматически превращаться в оценку здоровья.

### 5.2 Activity — 20%

WHO рекомендует взрослым 150–300 минут умеренной аэробной активности в неделю либо эквивалент интенсивной активности. Поэтому минуты активности являются основной объективной метрикой Activity.

#### Active minutes

| Минуты умеренной/эквивалентной активности в неделю | Score |
|---|---:|
| 0 | 0 |
| 30 | 20 |
| 60 | 40 |
| 100 | 60 |
| 150 | 80 |
| 300 | 100 |
| >300 | 100 |

Значения между контрольными точками интерполируются.

Превышение 300 минут не даёт дополнительного бонуса внутри Activity: LifeGame не превращает здоровье в соревнование по объёму активности.

#### Steps

Шаги являются **поддерживающей**, а не основной метрикой.

Продуктовый профиль:

| Средние шаги/день | Score |
|---|---:|
| <2 000 | 0–20 |
| 2 000–4 000 | 20–40 |
| 4 000–6 000 | 40–60 |
| 6 000–8 000 | 60–75 |
| 8 000–10 000 | 75–95 |
| ≥10 000 | 95–100 |

10 000 шагов не считается медицинской нормой. Шаги не должны одновременно получать полный вес и дублировать тот же объём движения через active minutes.

#### Distance / active calories

Используются как дополнительные показатели при наличии источника. Их внутренний вес должен быть ограничен, чтобы не получить тройной учёт одной и той же физической активности.

### 5.3 Training — 15%

Training оценивает не абсолютный объём движения, а устойчивость тренировочной системы.

Внутренние веса:

| Метрика | Вес внутри Training |
|---|---:|
| Frequency | 30% |
| Duration | 20% |
| Regularity | 20% |
| Load / recovery balance | 30% |

#### Frequency

Базовый продуктовый профиль:

| Тренировок/неделю | Score |
|---|---:|
| 0 | 0 |
| 1 | 30 |
| 2 | 60 |
| 3 | 80 |
| 4 | 90 |
| 5+ | 90–100 |

5+ тренировок не дают автоматического преимущества: дополнительный объём должен оцениваться вместе с восстановлением.

#### Duration

Продолжительность оценивается относительно типа тренировки и личного паттерна. Универсальная «идеальная длительность» не задаётся.

#### Regularity

Оценивается стабильность частоты тренировок за 28 дней, а не единичная удачная неделя.

#### Load / recovery balance

Этот показатель связывает Training и Recovery, но **не переносит Recovery score внутрь Training напрямую**. Используются признаки перегрузки, слишком быстрых изменений объёма и недостатка восстановительных дней.

### 5.4 Nutrition — 15%

Nutrition 1.0 не пытается диагностировать качество питания по калориям или макронутриентам без надёжного источника.

Внутренние веса:

| Метрика | Вес |
|---|---:|
| Regularity | 30% |
| User nutrition regime adherence | 30% |
| Subjective quality | 25% |
| Water | 15% |

#### Water

Вода является supporting metric. Универсальная фиксированная норма вида «2.5 л = 100» не используется.

### 5.5 Lifestyle — 15%

Внутренние веса:

| Метрика | Вес |
|---|---:|
| Alcohol | 20% |
| Smoking | 25% |
| Nicotine | 15% |
| Stress | 15% |
| Mood | 10% |
| Subjective wellbeing | 15% |

Поведенческие данные не превращаются в медицинские диагнозы.

Для алкоголя, курения и никотина предпочтительна оценка частоты и тренда, а не резкое наказание за единичный эпизод.

Объективные и субъективные данные остаются раздельными до стадии нормализации.

### 5.6 Body — 10%

Внутренние веса:

| Метрика | Вес |
|---|---:|
| Weight trend | 35% |
| BMI / contextual body composition proxy | 25% |
| Resting HR | 20% |
| BP | 20% |

Если Resting HR уже используется с достаточным весом в Recovery, его вес в Body должен быть снижен до 0, а перераспределение веса должно происходить только после отдельной валидации. Это правило предотвращает двойной счёт.

BMI является контекстной производной метрикой и не используется как самостоятельный медицинский диагноз.

Артериальное давление вводится вручную и отображается как медицински значимый показатель с осторожной формулировкой. LifeGame не определяет наличие заболевания.

## 6. Основной расчёт Health Index

После расчёта всех доступных факторов:

H_raw = Σ(W_f × F_f) / Σ(W_f_available)

где W_f_available — веса факторов, по которым существует достаточное количество валидных данных.

После этого применяется smoothing:

H_final = α × H_raw + (1 − α) × H_previous

Конкретный α не должен быть одинаковым для всех ситуаций: свежесть и качество данных могут влиять на его выбор.

Ограничение максимального суточного изменения должно быть задано после тестирования реальных сценариев.

## 7. Coverage и отсутствие данных

Отсутствие данных **не считается плохим здоровьем**.

Data Coverage — доля доступного веса модели.

Правила:

- <40% — **Insufficient data**
- 40–69% — **Preliminary**
- ≥70% — **Full**

При Coverage <40% числовой результат может существовать технически для диагностики, но пользовательский интерфейс не должен представлять его как полноценный Health Index.

## 8. Data Confidence

Data Confidence — отдельная характеристика качества оценки.

Учитываются:
- полнота;
- регулярность;
- свежесть;
- надёжность источника;
- качество измерения.

Confidence **не изменяет Health Index**.

Он влияет только на интерпретацию:
- High confidence;
- Medium confidence;
- Low confidence.

Ручной ввод не считается автоматически плохим источником.

## 9. Recency

В пределах 28-дневного окна новые наблюдения получают больший вес:

r(d) = exp(-λd)

λ определяется классом метрики.

На первом этапе используются три класса:

- **Fast** — настроение, субъективное восстановление, стресс, отдельные поведенческие события;
- **Medium** — сон, активность, тренировки;
- **Slow** — вес и другие медленно меняющиеся показатели.

Точные коэффициенты λ должны быть закреплены после отдельной серии тестов.

## 10. Constraint — ограничитель индекса

Health Index и Constraint являются разными сущностями.

Health Index показывает общую устойчивость системы.

Constraint показывает фактор, который сильнее всего ограничивает текущий результат.

Для фактора:

Constraint_f = W_f × (100 − F_f)

Главным ограничителем становится фактор с наибольшим Constraint_f, если его дефицит превышает минимальный порог значимости.

Это предотвращает ситуацию, когда высокий общий индекс скрывает критический локальный фактор.

Пример:

Health Index = 77

Recovery = 35

Пользователь должен видеть:

**HEALTH INDEX 77 / 100 — Good**

**MAIN CONSTRAINT**  
Recovery — 35 / 100

Недостаточное восстановление сейчас сильнее всего ограничивает текущую устойчивость системы.

Constraint не является медицинским диагнозом.

## 11. Диагностика

Диагностика должна объяснять:

1. какой фактор ограничивает систему;
2. какие метрики сформировали этот фактор;
3. что изменилось за 7 дней;
4. какое действие имеет наибольший приоритет.

Формат:

**Основной фактор:** Recovery

**Что влияет:** нерегулярный сон и недостаточное восстановление.

**Изменение:** Recovery снизился на X пунктов за 7 дней.

**Приоритет действия:** восстановить регулярность сна.

Нельзя выдавать медицинские диагнозы, причинно-следственные утверждения без достаточных данных или рекомендации, требующие клинической оценки.

## 12. Окна расчёта

- **28 дней** — основной Health Index;
- **7 дней** — краткосрочная диагностика;
- **90 дней** — долгосрочный тренд.

90-дневное окно не заменяет 28-дневную основу текущего индекса.

## 13. Защита от двойного счёта

Одна физиологическая характеристика или одно физическое действие не должны многократно повышать/понижать индекс без обоснования.

Примеры:

- шаги и active minutes не получают полный независимый вес за один и тот же объём движения;
- resting HR не получает полный вес одновременно в Recovery и Body;
- Training duration не должен автоматически дублировать тот же объём в Activity;
- производные показатели не должны повторно учитывать исходную метрику без отдельной методологической причины.

## 14. Что не входит в Health Index напрямую

Следующие данные могут собираться для контекста, но не должны автоматически влиять на индекс:

- температура;
- отдельные медицинские события;
- диагнозы;
- лекарства;
- лабораторные показатели;
- единичные аномальные измерения без проверки качества данных.

Их наличие не превращает LifeGame в медицинскую систему.

## 15. Источники данных

Этап 1: ручной ввод.

Этап 2: автоматизация доступных метрик через Apple Health / HealthKit и другие разрешённые источники.

Каждое значение должно иметь:
- источник;
- timestamp;
- тип измерения;
- признак качества/валидности, если он доступен.

Application слой преобразует raw data в нормализованные метрики; Index работает только с разрешённым контрактом данных.

## 16. Архитектурная граница

Health Index не хранит пользовательские данные.

Направление:

Health Domain → Application → Health Index → Diagnosis → Presentation

Index получает только необходимые нормализованные данные и возвращает:

- итоговый score;
- factor scores;
- coverage;
- confidence;
- constraint signals;
- diagnostic signals;
- methodology metadata.

Persistence, authentication, UI и HealthKit не должны попадать внутрь расчётного слоя.

## 17. Внешние основания параметров

При формировании базовых продуктовых параметров используются официальные рекомендации:

- CDC — рекомендации по продолжительности сна взрослых: https://www.cdc.gov/sleep/about/
- CDC — рекомендации по физической активности взрослых: https://www.cdc.gov/physical-activity-basics/guidelines/adults.html
- WHO Europe — рекомендации по физической активности: https://www.who.int/europe/news-room/fact-sheets/item/physical-activity

Эти источники используются для калибровки продуктовой модели, а не для утверждения, что Health Index является клиническим инструментом.

## 18. Параметрическая валидация

Параметры прошли математическую сценарную проверку:

- Fast half-life: 3 дня;
- Medium half-life: 14 дней;
- Slow half-life: 28 дней;
- smoothing α: 0.35;
- максимальное суточное изменение: ±8 пунктов;
- чувствительность верхнего уровня соответствует весам факторов.

Эти параметры являются baseline продукта и не являются медицинскими нормами.

## 19. Статус модели

**BASELINE / PLANNED.**

Параметры recency, smoothing и daily cap валидированы; вычислительный код Health Index реализован как первая техническая версия и требует дальнейших интеграционных тестов.

Архитектурная схема, факторы, веса верхнего уровня, target-band принципы, базовые внутренние веса и механизм Constraint согласованы как основа Health 1.0.

До статуса IMPLEMENTED необходимо отдельно проверить:

1. конкретные коэффициенты recency λ;
2. коэффициент smoothing α;
3. максимальное суточное изменение;
4. чувствительность каждого внутреннего веса;
5. граничные значения всех нормализаторов;
6. поведение конфликтующих метрик;
7. реальные пользовательские сценарии;
8. пользовательские формулировки диагностики.

После этой валидации модель может быть реализована в source/index/health/ без переноса бизнес-логики в Presentation.
